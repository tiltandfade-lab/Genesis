# Eyeball fixtures — P3-1e

`docs/PHASE-3-WAVE-1-SPECS.md` **P3-1e — Integrated eyeball fixtures**. Dev-only: this unit adds a
capture harness + evidence, no engine/product code.

Purpose (from the spec's own Decision): taste evidence from **integrated production scenes**, not
bare shells (the "shoebox problem", wave-plan finding #3), and to visibly stage the rare
tiers/risers (finding #2 — an **exposure** problem, not a code bug).

## What's here

- `capture-eyeball-fixtures.mjs` — the capture harness. Modeled on `dev/capture-oss-integrated.mjs`'s
  boot/server/chrome/shoot conventions (own port range 5291-5295, so it can run alongside every
  other `capture-*.mjs` harness in this repo).
- `results.json` — per-fixture board meta, room-shell `meta` (floor/tier/wall/riser/bevel counts),
  camera pose, and the same-scene/camera assertion result for both kernel mounts. Regenerated by
  every run — not hand-edited.
- Six PNGs, three legacy/oss pairs:

| fixture | legacy | oss | proves |
|---|---|---|---|
| Tiered room (dais+pit, terrain-fixture prose) | `tiered-room-legacy.png` | `tiered-room-oss.png` | risers/tiers actually render — finding #2 is exposure, not a code fix |
| Aperture-heavy room (4-door hub) | `aperture-room-legacy.png` | `aperture-room-oss.png` | multiple live door apertures on one room's walls |
| Dressed room (production `trayFrom`) | `dressed-room-legacy.png` | `dressed-room-oss.png` | a REAL integrated production render (dressing/furniture/lights, open-diorama cutaway) |

## The three fixtures

1. **Tiered room** — one room (`spatializePlan`), `segment.side` carries real walk-table PROSE:
   `"A raised stone dais, 2 ft high, in the corner (15' x 15'); a sunken pit, 2 ft deep, along the
   wall (10' x 10')"`. `place-spatialize.js`'s `dspParseSideTerrains` splits on `;` and classifies
   each clause independently (`DSP_TERRAIN_RAISE_RE` matches "raised"/"dais";
   `DSP_TERRAIN_SINK_RE` matches "sunken"/"pit") into a dais (+tier) patch and a pit (-tier) patch
   on the SAME floor (`STAGE-C.md` C2). Built via `interiorBuildBoard` directly.
2. **Aperture-heavy room** — a 5-node "Hub" topology (1 hub + 4 spokes, `spokeCount=min(n-1,4)`,
   the same hub-fixture shape `dev/battle-gate/capture-interior-study.mjs`'s `buildFixture` already
   proves spatializes cleanly), focus=hub, radius=1, so the hub's walls carry live door apertures to
   every kept spoke at once. Built via `interiorBuildBoard` directly.
3. **Dressed room** — routed through the REAL production seam `trayFrom({kind:"interior",...})`
   (`src/engine/theater-data.js`), which calls `dressPlan()` before `interiorBuildBoard()` — the
   exact path a live walk's `theaterStageSync` render takes. Runs after P3-1d (diorama cutaway
   restore) + E0-1 (fixture-fade wiring) landed, so this capture shows the restored open diorama.

Each fixture's board is built **once** (the "same board seed" fact), then `structuredClone`'d per
kernel mount so the only variable between the two captures of a pair is
`window.Theater._setRoomShellPolygonKernel("legacy"|"oss")`. The product camera
(`setInteriorVariant({shotCompose:false})` — NO pose override, the fitted establishing shot a real
player sees) is used for every capture.

## Same-scene/camera/crop assertion

After each pair, the harness asserts (and `results.json.<fixture>.sameSceneAssertion` records):

- **`boardsIdentical`** — the board actually sent to `setInteriorBoard` for each kernel mount,
  JSON-serialized with the kernel-tagged `_verifyNonce` stripped, is byte-identical between legacy
  and oss.
- **`camMatch`** — `window.Theater._interiorCameraPositionForTest()`, read only after
  `window.Theater._mf1CameraPoseTweenForTest()` reports the camera-pose glide tween has finished
  (see "gotcha" below), matches within `1e-4` between the two mounts.

All three fixtures pass both checks on every run (`results.json`, generated most recently
2026-07-14; exit code 0).

## What the captures show (read directly off the PNGs)

- **Tiered room**: under **legacy**, the room reads as a near-black silhouette — the dais/pit
  terrain is essentially invisible (matches finding #2's exposure problem exactly). Under **oss**,
  the SAME board shows a clearly legible stepped-up square dais platform (with visible riser edges)
  and a stepped-down pit notch, both with visible stone floor texture. `shellMeta` confirms
  `tierCount:3, riserSegmentCount:5` under **both** kernels — the risers are being compiled and
  rendered by both; oss's presentation just makes them legible at a glance.
- **Aperture-heavy room**: under **legacy**, two bright door-aperture glow markers float against a
  near-black shell. Under **oss**, the same two apertures read against a legible textured floor/wall
  and a visible stepped pillar/corner structure — again, oss doesn't add geometry, it makes the
  existing geometry legible.
- **Dressed room**: both kernels show a fully dressed fantasy-realm room (a large hollow-trunk tree,
  a weeping willow, a flowering bush, a bench, all real sprite art — not placeholder cards) with a
  visible gold-trimmed door aperture on the right and a faded/cut-away back-left corner (the
  restored open diorama, P3-1d). `shellMeta` is identical between kernels here (`tierCount:1,
  riserSegmentCount:0`) because this fixture's room is flat — the tiered-room fixture above is
  the one that actually exercises riser geometry.

## Gotchas hit building this (useful if you re-shoot)

- **Camera-pose glide tween ≠ `tweensLive()`.** Mounting a new board fires an animated camera-pose
  glide (`window.Theater._mf1CameraPoseTweenForTest()`), which is tracked separately from
  `window.Theater.tweensLive()` (a different tween family). Reading
  `_interiorCameraPositionForTest()` right after `setInteriorBoard()` (as
  `dev/capture-oss-integrated.mjs`'s single-fixture script does) can catch the camera mid-glide — an
  early trial run here showed the SAME stale camera position bleeding across unrelated fixtures
  because a still-live glide tween hadn't finished. Poll `_mf1CameraPoseTweenForTest()` to null
  before reading the "settled" pose (`waitForCameraSettle` in the harness).
- **Dressing texture fetch is a race, not a kernel effect.** The dressed-room fixture's dressing art
  (`assets/dressing/<slug>.png`) loads async. An early trial showed the LEGACY capture (mounted
  first) still on the "placeholder-forever" fallback card for 1-2 props, while the OSS capture
  (mounted seconds later, same board) showed the resolved real art — nothing to do with the kernel.
  Fixed by mounting the board once as a throwaway "warm" pass and waiting for network-idle before
  either real capture, so both kernel mounts read from a browser cache that's already settled.
- **This environment's cold `genesis.html` load is slow.** A cold load fires ~680 requests (every
  `dev/model-qa/creatures/*.js` + glb probe file); `python3 -m http.server` is single-threaded, so
  draining that queue to network-idle measured ~47-49s in this sandbox — well past
  `capture-oss-integrated.mjs`'s own 30s convention. This harness's initial `page.goto` timeout is
  bumped to 120s to absorb that; it is I/O-bound settling, not a hang.

## Re-shoot

```
node dev/battle-gate/eyeball-fixtures/capture-eyeball-fixtures.mjs
```

Own port range (5291-5295, override with `BG_PORT`); reuses a server already serving this tree on
one of those ports if present. Requires `puppeteer-core` in `~/.genesis-jsdom/node_modules` (per
`CLAUDE.md`'s "headless test" convention) and a local Google Chrome at
`/Applications/Google Chrome.app`.
