## Findings this run
- **BUG-01 REPRODUCED LIVE (🔧 — the regression list's headline, still PRESENT):** A branched roll resolved to the fail branch; its narration reached the player but its two `codex_update` events were **silently dropped**. Root cause confirmed: `resolveBranch` stamps branch events `source:"branch"` (dm.js:761), and `validateEvent` (dm.js:1224) only allows `source` ∈ {null,"detected","declared"} → every branch event fails the envelope check and no-ops. This is exactly the mutation-test-gap regression memory flagged: tests asserted the branch *label/narration*, not the mutated *state*. Recovery this run via the harness `patch` route-around (source:"declared"), as designed. **The bug-probe for this should stay PRESENT (not fixed).** Fix (future): add `"branch"` to validateEvent's allowed `source` enum (and/or stamp `"declared"`), plus a mutation test asserting branch events actually mutate `U`.
- **F-07 (codex-hygiene / warm-DM NPC-id collision, 🔧 — extends F-04):** At T10 the warm DM needed a name for the well's keeper and reached into the digest's `codexRoster`, grabbed **"Ospra"**, and reused `npc:ospra` for a brand-new, geographically-distinct role (tally-slate keeper at the Throat) — **but `npc:ospra` was already the tannery hide-scraper minted at T3** (a different person, different place). Its `codex_update {role:"well-keeper…"}` would have **overwritten/conflated the tanner's record.** (BUG-01 happened to drop the branch events so nothing auto-corrupted, but the intent was a canon collision.) Root cause = same as F-03/F-04: the roster shows a name but not enough established identity/role for the DM to know it's a LIVE distinct character, so a warm DM "borrows" a name that's already taken. **Fix:** the roster line should carry the entity's role/location (it partly does — but the DM still collided), and/or `codex_add`/reuse should warn when a name resolves to an existing known-distinct record. Clerk mitigation this run: re-landed the keeper as a DISTINCT record (`npc:the-tallywoman`, name deferred — slow-drip), leaving `npc:ospra` (the tanner) untouched. This is the sharpest single illustration of why "does the codex survive play?" needs de-dup/identity guards, not just persistence.
- **F-05 (roll-branches state-desync, 🔧):** On a **nat 20 / nat 1** against a BRANCHED rollRequest, `dmRollFor` (src/world/dm.js:733-735) correctly falls through to the live two-turn flow (crit-magnitude needs the live lens turn) — BUT it clears only `GS.dm.rollReq` (line 701), leaving **`w.dm.rollReq` still set** (verified in state.json after the fall-through). `resolveBranch` deliberately clears BOTH (line 766, with a comment that render.js re-hydration would otherwise re-fire the branch) — the fall-through path is missing that same clear. Consequence: on re-render / a second roll call, the persisted request re-hydrates and can **re-fire the roll**. In the harness a subsequent `roll` re-consumed `w.dm.rollReq` and rolled again. Fix: the nat20/1 fall-through must also clear `w.dm.rollReq` (mirror resolveBranch's line 766). Likely the same regression family as memory's BUG-01.
- **F-06 (harness observability, 🔧 harness):** When a branched roll falls through to live (nat20/1), the rolled **total is not persisted** to `U`/`GS` — it lives only in the ephemeral `__pendingRoll` printed to stdout. A stateless per-process harness that doesn't capture that stdout **loses the die result** (and thus the crit/fumble spike). Cost this run: T3's first roll was a nat-spike whose total was lost; recovery required a re-roll (→10, fail), silently discarding whatever the spike was. Fix: persist the fall-through roll (total + rolls + crit) into `w.dm.pendingRoll` so it survives a process boundary; also the harness `roll` cmd should print `pending` unconditionally. *(Integrity note: T3's re-roll is a minor distortion — a possible nat20 crit-success on Batgal's trail may have been discarded — but nothing was ever shown to the player and the persisted rollReq confirmed the check was still pending, so recovery was legitimate.)*
- **F-03 (codex-survival, 🔧 — HEADLINE):** The DM naturally records what it learns about an NPC as `codex_update {id, note:"free prose"}`. But `codexUpdate(w,id,patch)` (src/world/codex.js:126) only merges `patch.fields` / `patch.dm` / `patch.status` — **there is no `note` field, so every note is silently dropped.** Verified: after 2 turns of rich Corran/Maddan notes, both records still have `fields:{}` `dm:{}`. **The DM's accumulated understanding does NOT survive into the codex** — precisely the failure Run 2 exists to catch. A memoryless future DM re-reading the codex would get the engine-rolled atoms back but NONE of the interpreted knowledge play generated. **Fix options:** (a) SEAT-PROMPT must teach `codex_update {id, dm:{key:val}}` / `{id, fields:{key:val}}` as the ONLY way to persist knowledge (no `note`); and/or (b) make `codexUpdate` accept a `note` that appends to `dm.notes[]` so the intuitive shape just works. (b) is the robust fix — the seat will keep reaching for `note`. Ties to memory's "codex survives play" test intent + [[project-genesis-codex]].
- **F-04 (codex-hygiene, 🔧):** Maddan Strole exists as TWO records — `npc:maddan-strole` (contacted/known=true this run) and a roster twin `npc:maddan-strole-the-netmender` (soft/unknown, from Run-1 prep). Same NPC, split identity. A memoryless DM sees them as two different people in the roster. Codex needs de-dup / alias-merge on contact (when the DM contacts `npc:maddan-strole`, the `-the-netmender` twin should merge, not linger). Likely predates Run 2 (prep-mint vs play-mint collision).
- **F-02 (event-payload field-name drift, 🔧/prompt):** Two more events silently no-op'd on intuitive field names: `discovery` reads `payload.what` + needs `makeNode:true` to create a map node (DM sent `{name,desc}` → ledger "Discovered: something new", no node); `fact_canonized` reads `payload.what` (DM sent `{text}` → ledger "Canon fact recorded: ?"). `clock_advanced` uses `{clockId, delta}` not `{id, by}`. Same root cause as F-01/F-03: **a memoryless seat, absent an EXACT per-event payload schema, uses natural field names the engine drops without error.** Corrected in my seat prompt; the real SEAT-PROMPT.md must carry the exact payload field names for the ~15 most-used events + a worked example each, or events degrade to no-ops in production.
- **F-01 (roll-branches, 🔧/prompt):** DM seat emitted `rollRequest.branches = {success:"prose", fail:"prose"}` (bare strings, no `nearMiss`). Engine `sanitizeRollRequest` (src/world/dm.js:646) requires each branch to be an OBJECT `{narration, events}` with a numeric `dc`; it **stripped the whole set** to a bare rollRequest ("malformed branch set" warning) → lost local resolution + degrees-of-failure, forcing a live-resolution follow-up turn. Partly my distilled seat-prompt's fault (it modeled the loose string shape) — **but that's the signal**: the branch contract is finicky enough that a memoryless model won't hit it without an exact schema in SEAT-PROMPT.md. Fixed my seat prompt to teach the strict 3-branch object shape; T2+ should resolve locally. Relates to memory BUG-01 (roll-branch regression class). **Recommendation for the real SEAT-PROMPT.md: teach the strict branch schema verbatim + a worked example, or roll-branches silently degrades to bare live turns in production.**
