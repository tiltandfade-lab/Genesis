- **SET-01-F2** (harness usability, adjacent to known BUG-08) When a nat-20/nat-1 on a branched `rollRequest` correctly falls through to live resolution (`roll` returns `resolvedLocally:false, liveResolutionNeeded:true`), the fall-through `pending.action` + die live ONLY in that single `roll` invocation's stdout `__pendingRoll` — nothing is persisted to `w.dm.pendingRoll`. Engine BUG-08 itself is known/documented; not re-filing it.

- **SET-02-F2** (branch-carried `social_check.total` is decoupled from the live roll — MED, contract/seam) In a `rollRequest.branches` resolution the harness rolls the real d20 to SELECT the branch, but the branch's `social_check` event carries a **pre-authored literal `total`** that the DM wrote blind (it can't know the die). `resolveBranch` applies the branch events as-authored, and the `social_check` handler (`src/world/dm.js:2984`) grades the committed attitude shift against **`p.total`** (the literal), NOT the live d20 that chose the branch. Suggest: in `resolveBranch`, inject the actual resolved d20 total into any branch `social_check.total` (override the literal), or have the seat OMIT `total` in branch social_checks and let the resolver use the live roll.

- **SET-04-F2** · MED · **`item_changed` has no affordability backstop — an overspend silently clamps instead of refusing.** `sh.gold = Math.max(0, before + p.gold)` (src/world/dm.js:2421) floors the purse at 0 but never rejects a purchase larger than the purse, and the `add[]` still lands. So a DM that trusts a player's "I buy the warhorse" and emits `{add:[warhorse], gold:-75}` for a 9-gold PC hands over the 75g item and simply zeroes the purse — the buyer got a warhorse for 9 gold. The affordability gate rests ENTIRELY on the seat's fiction (which it can't even see the number for — cf. F1). In a live bridge with a weaker seat this is the real economy-exploit surface. Repro: apply `item_changed {gold:-N}` with N > current gold → gold floors to 0, returned `gold` delta = -(had), item still added. Fix: refuse (or flag) an `item_changed` whose negative `gold` exceeds `sh.gold` when it's a purchase (has `add[]`), OR surface a `{ok:false,reason:"cannot-afford"}` the seat can react to — mirroring the bastion claim's `cannot-afford:price` guard at dm.js:3901 (which the buy/sell path lacks). Distinct from F1: F1 = can't see gold; F2 = engine won't enforce it either. (Set 04, Rennick, theme B.)
