# BattleMap / TownTray Procedural Composition

This study promotes the FFT composition research from a loose reference package into a **high-priority shared
engine direction**. It does not authorize implementation and it is not a final build spec. Wave 12 still owns the
complete dependency graph, budgets, release gates, and build authorization; Wave 10 P10.10 still owns performance,
device, and accessibility decisions.

## 1. Binding direction

Adam's ruling, 2026-07-22:

> "ok these are high priority items and need to be analyzed in depth to be implemented into the procedural engine, if we can find a way to build maps nearing the quality of the FFT standard maps then we have ourselves a money printer.
>
> this is the battle map module, but also can be any town tray model as well, and i think with the automatic UV unwrapping that we should have implemented, we should be able to determine what shape sprites need to be generated for each surface/angle type in the game"

The accepted direction is:

1. **FFT-grade structural composition is a high-priority engine target.** “FFT-grade” means finite, legible,
   tactically expressive boards with coherent elevation masses, strong landmarks, meaningful approaches, shaped
   negative space, and readable fixed-production-view composition. It does not mean copying an FFT map, asset, texture, code
   path, or exact arrangement.
2. **BattleMap and TownTray share one composition compiler.** A market, courtyard, tavern, wilderness pocket, and
   dungeon chamber should not be five unrelated scene systems. They are recipes over one grid/surface, route,
   connector, reservation, provenance, and rendering contract.
3. **The clay-room proof is the first rung.** One small real-roll room proves the compiler and remains in the
   regression corpus. Multi-room, town, travel, and relational scenes consume the same outputs later.
4. **Surface art is generated by a compact surface/projection contract, not bespoke per-map painting.** Geometry
   decides the surface shape. Art supplies reusable panels, strips, decals, and component faces in declared
   projections. Runtime assembly clips, rotates, repeats, and mounts them.
5. **The UV premise is corrected below.** Genesis has production procedural UV projection for generated room
   architecture; it does not have a production general-purpose automatic UV unwrapper. General offline unwrap
   remains useful for reusable complex assets but should not become a runtime dependency for generated boards.

**Later fixed-camera amendment, 2026-07-22:** Wave 3 section 12.13 supersedes this study's original four-player-yaw
acceptance assumption. Genesis now targets one stable production yaw/pitch/projection family with governed pan,
zoom, focus, recenter, and cutaway/ghosting; player rotation is not a prototype/playable-MVP requirement. Earlier
four-view language below records the research path and is interpreted by the updated production-view gates. Optional
nonproduction yaws may diagnose malformed geometry or fragile composition, but do not require equal beauty,
production-quality unseen backsides, or player access.

## 2. What “near the FFT standard” means for Genesis

The target is the compositional standard visible in the supplied reference corpus, translated into Genesis's own
mechanics, rolls, art direction, and procedural constraints:

- a board reads as a small place, not a noisy height map;
- two or three large elevation ideas dominate, rather than unrelated per-cell bumps;
- every traversable height change has a visible, mechanically shared connector;
- one landmark or structural mass gives the scene identity and affects play;
- a primary movement spine is immediately legible;
- a secondary route, refuge, flank, shortcut, or risk/reward position appears only when the licensed footprint and
  program support it;
- void, water, cliff, wall, building mass, and deliberately open floor shape meaningful negative space;
- deployment, contact, objective, and retreat space are composed with the terrain rather than scattered afterward;
- props reinforce the architecture and routes instead of carrying the whole composition;
- the map remains tactically honest through the fixed production view and its governed focus/cutaway states; and
- the same map can exist first as clay, then as a dressed Genesis board, without changing mechanics.

This is a **structural** bar. Pixel citizens, Genesis materials, dynamic light, the shared shell, and the
EngagementLens remain Genesis's presentation. The supplied images and GaneshaDx are reference and research only.

## 3. Current-engine audit

Genesis is not starting from zero. The existing engine already owns the following landed pieces, although several
are not yet joined into the accepted future exact-cell battle authority.

### 3.1 Spatial truth already present

`src/engine/place-spatialize.js` already supplies:

- row-major five-foot `VOID`, `FLOOR`, `WALL`, `DOOR`, and `WATER` cells;
- deterministic room footprints derived from rolled dimensions;
- rect, circle, octagon, ellipse, L, T, cross, and cave room shapes;
- exact rooms, corridors, doors, room roles, depth, and graph provenance;
- signed tier values and rolled elevation profiles including dais, sunken center, split level, terrace, gallery ring,
  and chasm/shaft;
- side-text elevation patches that outrank generic profile placement;
- door-aperture tier protection;
- corridor crossing detection with a reserved `bridge:true` marker; and
- a basic four-neighbor reachability proof.

### 3.2 Arrangement and reservation already present

`src/engine/room-grammar.js`, `place-dressing.js`, and `place-distribution.js` already supply pieces of a composition
language:

- ALIGN, PAIR/FLANK, FOCAL, RHYTHM, and CLEAR primitives;
- door/apron, center, wall-adjacency, and occupied-cell exclusions;
- deterministic focal, blocker, wall-hang, filler, light-affine, and seam placement;
- a staging reserve rather than silent noun deletion; and
- deterministic provenance for incidental realization.

These passes are valuable but local. Their current CLEAR model is mostly center 2x2 plus door aprons; the room
grammar does not yet own complete aisles, approach lanes, tactical regions, deployment, objectives, or typed
vertical traversal. Dressing can reinforce a composed map, but it cannot create that map after the fact.

### 3.3 Geometry and camera already present

`src/ui/theater-room-mesh.js`, `theater-shot.js`, and `theater-boot.js` already supply:

- continuous floor polygons and volumetric wall/riser runs;
- shape-generic contours, apertures, bevels, caps, footing, and trim;
- logical cell-to-triangle diagnostics;
- four diagonal camera candidates and player quarter-turns;
- action-cluster camera fitting;
- actor/objective/focal-light anchors; and
- dynamic wall, pillar, door, and furniture occlusion treatment.

The camera composes subjects after placement. It does not decide whether the board itself contains a readable
route hierarchy, landmark, elevation composition, or tactical opportunity.

### 3.4 The central missing layer

The current pipeline jumps too quickly from legal room cells and simple elevation recipes to local object
placement and rendering. It lacks one shared product that says:

- these cells form the main plateau;
- this is the primary route and this is a materially distinct optional route;
- this stair, ramp, climb, bridge, or drop is the legal relationship between surfaces;
- this area must stay open for arrival/deployment;
- this is the objective or landmark approach;
- this obstruction creates a tactical choice rather than random blockage;
- this negative space shapes the board; and
- these decisions remain legible at the four player yaws.

That missing product is the proposed **`TacticalCompositionPlan`**.

### 3.5 Exact-cell combat is accepted direction, not current live authority

`docs/BATTLEMAP.md` records an important migration fact: the live combat resolver still owns the legacy 12-zone
band-by-lane model. The future exact `SpatialPlan` cell authority is accepted, but unimplemented. Likewise, current
room tiers primarily reach the renderer; a rendered riser does not by itself prove movement cost, climb, jump,
high-ground, line-of-sight, or occupancy mechanics.

Therefore this composition module cannot be accepted as a renderer-only upgrade. C1D first establishes the
exact-cell battle spine. C1H then composes and validates the same cells/surfaces/connectors that movement, targeting,
pathfinding, cover, elevation, and rendering consume. The legacy zones may later be derived from those cells as a
text, accessibility, small-screen, or degraded projection; they must not remain a second tactical truth.

## 4. UV audit: what exists and what does not

### 4.1 Production behavior that exists now

The generated room shell uses deterministic UVs by construction:

- floor, cap, bevel, and other horizontal faces use world-aligned X/Z projection;
- wall and riser faces use a continuous perimeter-distance U coordinate and height V coordinate;
- adjacent wall segments therefore retain texture continuity, with one expected seam on a closed ring;
- known box/component faces use planar per-face mappings or authored source UVs; and
- the renderer can route different materials to floors, walls, and darker risers.

This is not a fallback of lesser quality. For disposable generated walls, floors, cliffs, plazas, roofs, and terrain
masses, deterministic world/local projection is usually preferable to arbitrary atlas unwrap: texel scale stays
stable, seams are predictable, repeated generation is cheap, and a map never waits for runtime WASM packing.

### 4.2 General automatic unwrap is not implemented

The repository records the general unwrap lane as unlanded:

- `xatlas-three.UVUnwrapper` was proven importable in a scratch Node environment;
- the actual WASM/worker unwrap was not captured;
- `xatlas-three` was deferred and a later watlas direction never fired; and
- `docs/KENNEY-SOCKET-WAVE.md` explicitly says UV unwrap is **not installed**.

Therefore Genesis must not design this module as if arbitrary runtime meshes already receive a production-quality
automatic atlas.

### 4.3 Correct ownership by surface class

| Surface/asset class | UV ownership | Reason |
|---|---|---|
| Generated floor, plaza, roof deck, wall, riser, cliff, terrain mass | Deterministic world/local planar or triplanar projection | Stable scale, cheap regeneration, no per-map asset bake |
| Generated slope or ramp | Local tangent/bitangent projection derived from the slope frame | Texture follows the actual surface without an atlas |
| Repeated trim, stair edge, rail, curb, beam | Run-distance U plus profile-distance V | Continuous along procedural runs |
| Simple faced box or component kit | Authored canonical face UVs and named face panels | Reuse and state assembly are more important than generic unwrap |
| Reusable complex donor mesh or generated chassis | Authored UVs when valid; otherwise offline automatic unwrap/pack | The asset is baked once, validated, and reused |
| One-off disposable generated architecture | Never require offline unwrap | World projection or triplanar material is the correct contract |
| Decal | Strict top/front or owning-surface frame | The decal is a bounded mark, not a wrapped solid |

Offline unwrap should be promoted only when a real reusable complex asset or paint-over bake needs it. It remains a
build-time foundry step with topology validation, stable recipe hash, remapped attributes, atlas metadata, gutters,
and turntable QA. It must never unwrap a live walk during play.

## 5. The shared compiler boundary

The proposed data flow is:

```text
rolls / walk facts / place or venue program
  -> SpatialIntent
  -> SpatialPlanV2 legality
  -> TacticalCompositionPlan
  -> SurfaceAssemblyPlan
  -> BattleMap | SceneTray | TownTray projection
  -> ShotPlan + materials + sprites + DM-seat fact anchors
```

### 5.0 Provisional migration through the current tree

The smallest non-big-bang path through current owners is:

```text
spatializePlan() baseline envelope/cells/portals/current tiers
  -> semanticizePlan() room roles, depth bands, scale domains
  -> composeTacticalPlan() new pure overlay/product
  -> bindWalkInteractables() + applyRoomGrammar() consume its slots/reservations
  -> dressPlan() + placeDistribute() consume its incidental regions/exclusions
  -> theater-data projection
  -> room-shell/surface assembly + ShotPlan
```

The first C1A scaffold can analyze and annotate the current plan without changing any cell. C1H can then promote a
bounded subset—regions, routes, typed connectors, reservations, and one elevation-mass family—behind explicit
parity/fallback gates. Existing elevation-profile code should move behind or feed the new owner incrementally, not
be deleted in a single rewrite. Existing placement passes remain useful consumers; duplicated CLEAR/apron formulas
should eventually converge on composition-owned reservations rather than receiving a fourth independent copy.

The exact module/file names, schema migration, and legacy-switch mechanics remain specification work. The boundary
above is the intended responsibility split, not build authorization.

### 5.1 Authority law

- Rolls and committed world state own nouns, purpose, extent, topology, known elevation intent, actors, objects,
  conditions, hazards, and secrets.
- `SpatialPlanV2` owns legal cells/surfaces, portals, occupancy classes, and graph reachability.
- `TacticalCompositionPlan` chooses and records one legal arrangement of licensed spatial facts. It may derive
  routes, regions, sight relations, and support geometry; it may not reroll or contradict a noun.
- `SurfaceAssemblyPlan` converts that composition into surface frames, material routes, mesh recipes, mount sockets,
  and UV methods. It owns no mechanics.
- BattleMap/TownTray rendering projects the same plan. Combat may promote actors from coarse anchors to exact cells,
  but may not replace the venue with an unrelated arena.
- The DM seat receives semantic facts and committed results. It may describe the arrangement but cannot open a
  blocked route, create high ground, move a landmark, or substitute a renderer guess for canonical geometry.

### 5.2 Conceptual `TacticalCompositionPlan` shape

This is a design shape, not a frozen schema:

```js
{
  id, version, seed, sourceRefs, modeFamily,
  envelope: { cells, boundary, portals, voids },
  regions: [{ id, kind, cells, tierRange, tags, sourceRefs }],
  surfaces: [{ id, layer, cells, tier, supportRef, clearance }],
  connectors: [{
    id, fromSurface, toSurface, kind, cells, delta,
    direction, width, capacity, capability, cost, sourceRefs
  }],
  routes: [{
    id, kind, fromAnchor, toAnchor, surfaceEdges,
    mobilityClass, materialDifference, sourceRefs
  }],
  anchors: [{ id, kind, cellOrRegion, facing, sourceRefs }],
  reservations: [{ id, kind, cells, hardness, sourceRefs }],
  placementSlots: [{ id, kind, cells, facing, footprint, sourceRefs }],
  relaxations: [{ rule, reason, before, after, sourceRefs }],
  diagnostics: { /* transparent measures; never one opaque quality score */ }
}
```

The `surfaces[].layer` field is reserved from the start but remains `0` in the first implementation. This prevents
new code from assuming forever that X/Z has only one traversable surface, while avoiding pre-alpha stacked-surface
scope.

### 5.3 Regions are overlapping semantic lenses

A cell may belong to several region views: a raised mass, the primary route, a deployment approach, and a landmark
apron. Regions are not mutually exclusive terrain tiles. They are named groups used by solvers, mechanics,
placement, diagnostics, and presentation.

Minimum region vocabulary:

- `open-floor` or `arena`;
- `elevation-mass` / `basin` / `rim`;
- `primary-spine`;
- `secondary-opportunity`;
- `threshold` / `chokepoint`;
- `deployment` / `arrival`;
- `objective-approach` / `interaction-apron`;
- `refuge` / `exposed`;
- `landmark-mass`; and
- `negative-space-boundary`.

The room or venue recipe decides which are meaningful. A closet may correctly have one open region, one threshold,
and no secondary route.

## 6. Composition passes

The compiler should be constructive and bounded: generate a small deterministic candidate family, reject hard
violations, score transparent soft goals, and record any relaxation. It should not run an unbounded search for a
mythical universal “best” map.

### Pass 0 - normalize licensed intent

Collect the exact room/venue footprint, portals, approach, room function, rolled shape, rolled or authored
elevation, water/void, landmark/object/hazard facts, encounter requirements, town thresholds, and persistent
changes. Classify each input as:

- **hard canon** - cannot move, remove, or contradict;
- **arrangeable canon** - must appear, but the compiler owns a legal position/form;
- **derived support** - ordinary stairs, retaining mass, curb, backing wall, or route relation required to realize
  canon; or
- **decorative opportunity** - may enter reserve without changing world truth.

### Pass 1 - board envelope and negative space

Resolve the finite stage boundary, playable floor, building/rock/void/water mass, portal faces, and required
threshold aprons. Negative space is planned before small props. It should create silhouette and route pressure, not
merely fill unused cells.

### Pass 2 - elevation-mass composition

Convert rolled elevation intent into a few coherent regions. Preserve explicit side-text terrain before generic
profile shaping. Prefer broad plateaus, basins, rims, terraces, and cuts over cell noise. Record the source and
degradation of every tier assignment.

The first version can continue to use discrete tier quanta. True slopes are a connector/render form, not permission
to replace the canonical elevation endpoints.

### Pass 3 - route and vertical-connector graph

Build the primary route between required anchors first. Add a secondary route only when it is materially distinct
and licensed by available geometry. Every adjacent-surface height delta receives one typed relation:

- stair;
- ramp;
- climb/ladder;
- jump/drop;
- bridge;
- lift or special mechanism; or
- blocked riser.

Pathfinding, combat cost/capability, animation, and rendering must consume the same connector id. A decorative stair
cannot create a legal route, and a legal ramp cannot vanish from the visualizer.

### Pass 4 - landmark and functional assembly

Place the licensed centerpiece, dominant building mass, tree, gate, altar, stall block, fountain, tower, or other
landmark into a slot that affects composition and play. Protect its approach, interaction footprint, sightline,
and relation to the primary spine. A room with no licensed landmark may use a dominant structural mass but may not
invent a new canonical object.

### Pass 5 - deployment, encounter, objective, and retreat

Reserve the party's approach-bounded deployment region, hostile or neutral arrival, objective interaction space,
reinforcement thresholds, and at least one honest retreat route when the fiction permits it. This pass consumes
encounter needs without hand-authoring a fixed encounter into the reusable venue.

For TownTray, the same reservations can remain dormant during social play and activate when SceneLineage promotes
the venue to BattleMap. The market does not regenerate at combat start.

### Pass 6 - structural blockers, cover, and functional furniture

Place walls, half-height masses, columns, counters, stalls, shelves, carts, rocks, trees, and other mechanical
obstructions so they reinforce regions and routes. Functional assemblies use ROOM-GRAMMAR primitives and sockets.
Cover may be asymmetric, but immediate deployment exposure, high-ground control, route count, and objective access
must be visible in diagnostics.

### Pass 7 - surface assembly and art mounting

Emit a `SurfaceAssemblyPlan` with one stable local frame per surface:

```text
origin O
normal N
tangent T
bitangent B
boundary / mask
material role
UV method and scale
edge/corner/run sockets
source and composition provenance
```

The frame is the bridge between procedural geometry and generated art. It tells the engine which projection a
panel or decal needs, which way grain runs, where a trim strip repeats, and how an interaction face mounts.

### Pass 8 - fixed-production-view composition and occlusion validation

Capture and evaluate the fixed production view at gameplay scale across governed overview, room/exploration, and
action/combat focus plus representative cutaway/ghosting states. Protect critical actor, objective, connector,
route, and landmark visibility. Dynamic cutaway may repair foreground obstruction, but it may not erase so much
architecture that elevation and negative space stop reading. Optional nonproduction yaw diagnostics may expose
malformed backsides, false adjacency, or candidate fragility without becoming player-facing beauty gates.

### Pass 9 - deterministic relaxation and fallback

Relax in named order and retain receipts. A provisional order is:

1. reduce incidental dressing;
2. move or reserve decorative assemblies;
3. shrink an optional noncanonical support footprint;
4. remove an optional secondary opportunity;
5. simplify the arrangement of a generic elevation profile while preserving its signed intent and explicit
   authored patches;
6. use the smallest mechanically honest connector form;
7. emit the legal clay representation and flag the failed beauty condition.

Never silently flatten a required elevation, delete a rolled noun, move a committed threshold, create an invented
route, or reroll the scene because the first candidate was awkward.

## 7. Surface and generated-art contract

Adam's proposed “shape sprites for each surface/angle type” is viable if **shape** and **view angle** are assigned to
the correct owners.

### 7.1 Geometry owns the final shape

Image generation should not paint a bespoke polygon for every floor or wall. The compiler owns the mesh boundary
and alpha/mask. Reusable art normally arrives as:

- a seamless or bounded material panel;
- an edge/trim strip;
- a convex or concave corner module;
- a strict front face for an architectural component;
- a strict top decal;
- a coordinated orthographic face set for a box-like object; or
- an isolated sprite/component mounted to a named surface socket.

The engine then clips, tiles, rotates, mirrors where licensed, and assembles it over real geometry.

### 7.2 A compact canonical surface-frame family

Do not generate separate art for north, east, south, and west. Orientation is a transform over one canonical local
frame unless lighting, writing, heraldry, damage, or material direction makes the reverse materially distinct.

| Family | Canonical source projection | Runtime use |
|---|---|---|
| `HORIZONTAL_TOP` | strict top / seamless panel | floors, plazas, roof decks, wall caps, platforms |
| `VERTICAL_FACE` | strict front / seamless or bounded panel | walls, building fronts, cliff faces |
| `RISER_RETAINING` | strict front, darker/denser material role | tier sides, terrace risers, curb/retaining bands |
| `SLOPE_PLANE` | strict orthographic face aligned to uphill tangent | ramps, roofs, embankments |
| `RUN_STRIP` | strict front or top strip with repeat axis | trim, curb, rail, stair edge, beam, gutter |
| `CORNER_CONVEX` | orthographic component or procedural geometry | outside corners and caps |
| `CORNER_CONCAVE` | orthographic component or procedural geometry | inside corners and junctions |
| `STAIR_TREAD` / `STAIR_RISER` | top panel / front panel | repeated stair construction |
| `BRIDGE_DECK` / `BRIDGE_SIDE` / `BRIDGE_SUPPORT` | top / front / profile | future crossing assembly |
| `ROOF_FACE` / `EAVE` | slope-plane / run strip | TownTray building masses |
| `WATER_OR_VOID_EDGE` | top decal/edge strip plus procedural body | shores, channels, pits, chasms |
| `SURFACE_DECAL_TOP` | strict top with alpha | blood, wear, tracks, scorch, cracks, floor marks |
| `SURFACE_DECAL_FRONT` | strict front with alpha | grime, signs, murals, wall damage |
| `MOUNT_FACE` | strict front component art | doors, levers, plaques, shop fronts, windows |

This is an art-generation manifest vocabulary, not a promise that every family needs custom art for pre-alpha.
Procedural material fallback is mandatory.

### 7.3 Orientation and camera are separate

A surface's angle means its **world/local normal and tangent**, not the player's current camera yaw. The mesh and
material rotate with the board. Only standees, certain billboards, and view-governed UI care about the camera.
Painting four camera-specific wall textures would create a combinatorial asset problem and lighting contradictions.

### 7.4 Material identity without texture explosion

Each realm/biome/town kit should define a small material family across semantic roles:

- ground/floor;
- structural wall;
- riser/retaining;
- roof/deck;
- trim/edge;
- wood/metal/stone support;
- water/void body and edge; and
- a small decal family.

The same family can vary through authored panel choice, deterministic tint/value bands, normals/roughness, wear
masks, and edge modules. It should not require one image per map, cell, compass direction, or camera.

## 8. Shared BattleMap and TownTray behavior

### 8.1 One venue, several projections

The canonical venue keeps stable surface, threshold, region, object, and actor ids across:

- town/exploration SceneTray;
- focused interaction or inspection;
- exact BattleMap combat;
- aftermath; and
- unmount/semantic compaction/remount.

TownTray may display a smaller active slice or coarser ambient citizen projection. BattleMap promotes legally known
actors and tactically material relations to exact cells. It does not swap in a different map.

### 8.2 Recipe differences, not engine forks

Mode/venue recipes tune composition priorities:

- **dungeon chamber:** portals, room function, elevation, landmark, encounter affordances;
- **market/courtyard:** public spine, stall/building masses, sightlines, access thresholds, citizen flow, same-venue
  combat reservations;
- **tavern/shop/interior:** counter/hearth/focal, aisles, door approach, functional furniture, limited deployment;
- **street/alley:** longitudinal spine, side entries, frontage, obstruction and pursuit thresholds;
- **wilderness pocket:** biome mass, path/crossing, cover, terrain exposure, landmark;
- **travel segment:** route choice and encounter mounting over a bounded grid or node/vector projection.

All recipes use the same region, connector, route, reservation, surface-frame, provenance, and diagnostic types.

## 9. Hard constraints and soft goals

### 9.1 Hard constraints

A candidate cannot ship when it:

- changes a committed noun, portal, route endpoint, or persistent delta;
- places an actor/object on an illegal or occupied footprint;
- blocks a required route, interaction apron, deployment, or threshold;
- makes a traversable height change without a connector;
- renders a connector the mechanics do not own;
- leaks a hidden actor, hazard, route, or secret through composition data;
- loses source provenance;
- produces unreachable required cells for a supported mobility class;
- changes result on save/load or remount; or
- depends on a camera-specific painting to make mechanics legible.

### 9.2 Soft composition goals

Candidate selection may score:

- small count and strong area share of coherent elevation masses;
- primary-spine legibility;
- material distinction of any secondary route;
- landmark dominance without route obstruction;
- useful negative space and silhouette;
- cover density by region rather than global average;
- deployment exposure and access to counterplay;
- objective approach variety;
- production-view visibility of actors, routes, connectors, and landmark across governed focus/cutaway states;
- value/light composition hooks; and
- sparse, architecture-led dressing.

There should be no universal black-box “FFT score.” A flat courtyard, one-way ambush, brutal chokepoint, isolated
balcony, or sparse road can be correct. Diagnostics explain the composition so corpus review can judge intent.

## 10. Diagnostics and QA corpus

### 10.1 Greybox diagnostics

The clay/debug view should be able to show, without changing the scene:

- region ids and area shares;
- cell tier and stable surface id/layer;
- primary and secondary routes by mobility class;
- connector kind, direction, height delta, width, and cost;
- hard and soft reservations;
- deployment, objective, landmark, and interaction anchors;
- blockers, cover, and line-of-sight summaries;
- source references on every committed element;
- constraint failures and the exact relaxation ladder used; and
- fixed-production-view occlusion/visibility failures by governed focus/cutaway state.

### 10.2 Acceptance ladder

1. **Baseline capture:** measure the current small clay room without changing behavior.
2. **One-room scaffold:** emit the composition/diagnostic product over the current legal room and prove no authority
   drift.
3. **One composed clay battlefield:** use a real Genesis roll to produce broad elevation masses, one primary spine,
   at least one typed connector, one licensed landmark/structural dominant, honest deployment/objective space, and
   production-view-readable clay captures across the governed focus/cutaway states.
4. **Dressed parity:** apply material and sprite/component families; mechanics, routes, reservations, and provenance
   remain byte-equivalent.
5. **Battle continuity:** exploration -> exact BattleMap plus EngagementLens -> damaged aftermath uses the same
   surfaces and ids.
6. **TownTray reuse:** the C2M market fixture uses the same compiler and promotes the same venue into battle.
7. **Structural portfolio:** distribute the structural risks below across the accepted Wave 2 twelve named golden
   sites as real rolls license, accumulating retained fixtures one at a time. They are not recreations of twelve
   FFT maps and the structural list does not replace the product/system corpus.
8. **Multi-room and relational growth:** only after the earlier fixtures remain green.

### 10.3 Suggested twelve structural coverage dimensions

These are twelve **structural coverage dimensions**, not twelve replacement golden sites. The product/system corpus
remains Wave 2's named guard-post, camp/service, dormant-place, commune, mine/workshop, prison/institution, natural-
lair, layered-control, contested-fortress, urban-institution, mixed-scale/dragon-domain, and anomalous/living/mobile
site roster plus its eight adversarial traces. The eventual corpus should distribute distinct structural problems
such as:

- stepped courtyard;
- basin and rim;
- switchback ascent;
- narrow bridge/crossing;
- broken wall and gate;
- rooftop/frontage slice;
- offset platform landmark;
- ravine or water channel;
- forest pocket and clearing;
- desert/rock mesa;
- market plaza with functional stalls/building mass; and
- tight interior whose valid result is intentionally simple.

Each retained fixture originates in Genesis rolls and records why its selected composition is legal. One golden
site may cover several structural dimensions, and no one-to-one pairing is frozen in advance.

## 11. Prototype-to-feature implementation ladder

This module follows the accepted **first scaffold, then feature goal** framework.

### 11.1 C1A scaffold - truth and diagnostic seam

- Keep the one small retained room.
- Add no new content breadth.
- Establish stable composition ids, surface ids, provenance, and a greybox diagnostic read over existing geometry.
- Prove that composition remains a projection of canonical rolls.

This is low-medium bounded architecture/QA work once exact implementation files are audited. It is not the visual
quality claim.

### 11.2 C1H - one high-priority composed clay battlefield

Add a dedicated Stage-1 pass after the connected C1A-D battle spine and before broad travel/town rollout:

**Primary question:** can one real rolled room become a tactically and visually intentional battlefield—coherent
elevation masses, typed connectors, a readable primary spine, licensed landmark or dominant structural mass,
honest deployment/objective space, shaped negative space, and fixed-production-view legibility—without authored-map copying,
renderer-owned mechanics, or lost provenance?

C1H is the first meaningful composition-quality gate. It consumes the exact-cell BattleMap and mandatory
EngagementLens spine rather than postponing battle play until an entire map generator is beautiful.

### 11.3 C2 and TownTray reuse

- C2A/C2D prove that regions, surfaces, connectors, and persistent deltas survive room/mode transitions.
- C2M mounts a bounded real-roll market/town venue with the same compiler, promotes it to BattleMap, and remounts
  aftermath without replacing geometry.
- C3C and the later corpus passes add contrasting structural families rather than one large batch.

### 11.4 Later feature promotions

- stacked traversable surfaces and simultaneous upper/lower routes;
- richer bridge, roof, overpass, and interior/exterior assemblies;
- a complete surface foundry with offline unwrap for complex reusable chassis;
- expanded town/wilderness composition recipes;
- broader material and prop families;
- learned or solver-assisted candidate ranking trained only from accepted diagnostics/captures, never opaque
  unreviewed map authority.

## 12. Cost and maintenance assessment

| Work | Implementation cost | Ongoing maintenance | Why |
|---|---:|---:|---|
| Audit/diagnostic product over current room | Low-medium | Low | Most source data exists; needs stable ids and reports |
| Tactical-region candidate generation and scoring | High | Medium | New central algorithm, fixtures, relaxation/provenance |
| Typed vertical connectors shared by mechanics/render/pathfinding | Medium-high | Medium | Crosses spatial, combat, movement, render, and animation owners |
| One composed C1H clay battlefield | Medium-high after seam | Low-medium | Bounded content, but deep integration and visual acceptance |
| Four-yaw capture and occlusion gate | Medium initially | Low per fixture | Existing camera/occlusion helps; automation and thresholds remain |
| Surface-frame/material routing for procedural architecture | Medium | Low-medium per new family | Current UV projection is a strong base |
| Generated surface-panel/component art family | Medium per realm pilot | Medium with breadth | Compact family prevents compass/map combinatorics |
| General offline automatic unwrap foundry | Medium-high | Medium | WASM/worker/build tooling, remap, bake, gutters, QA |
| C2M TownTray reuse | Medium-high integration | Medium | Identity/remount/venue recipes more costly than mesh generation |
| Stacked traversable surfaces | High; future | High | Changes cell assumptions, pathfinding, occlusion, interaction, saves |

The largest risk is not triangle generation. It is keeping tactical legality, procedural composition, mechanics,
rendering, persistence, and remount on one data spine. A shared intermediate plan and retained fixtures reduce that
maintenance cost; separate battle/town generators would multiply it.

The accepted trim-sheet creation/runtime lane is specified at design level in `TRIM-SHEET-PIPELINE.md`. C1I now
follows C1H as a separate surface proof and does not replace this document's composition-first gate.

Performance budgets, target device ceilings, search/candidate caps, mesh/texture budgets, and accessibility
projections remain deliberately unchosen until P10.10.

## 13. Failure risks and controls

| Risk | Control |
|---|---|
| Maps become attractive but tactically false | Mechanics consume the same surfaces/connectors/routes as rendering |
| Procedural output becomes cell noise | Compose a few regions/masses before fine cells and dressing |
| One pretty seed hides fragility | Retained deterministic corpus, changed-seed tests, transparent diagnostics |
| Art asset count explodes by direction/angle | Canonical local frames, rotations, reusable panels/strips/corners |
| Auto-unwrap becomes a runtime bottleneck | World/local projection for generated architecture; offline unwrap only for reusable complex assets |
| Town and combat drift into separate venues | One venue id and `TacticalCompositionPlan`; SceneLineage changes precision, not place |
| Camera repair erases architecture | Four-yaw gate measures both subject visibility and retained mass |
| Solver silently deletes awkward rolls | Hard/arrangeable classification, named relaxation receipts, staging reserve, clay fallback |
| FFT reference becomes accidental copying | Use composition principles and Genesis rolls only; no imported code/assets/layout templates |
| Early scope delays the playable battle spine | C1A-D first; C1H is a retained quality pass before broad module rollout |

## 14. Decisions still open for later specification

The high-priority direction is accepted. These exact implementation decisions remain open until the relevant Clay
Pass is specified:

- candidate-generation algorithm and bounded search count;
- exact `SpatialPlanV2` / `TacticalCompositionPlan` schemas and migration;
- mobility classes and connector costs;
- how much of existing elevation profile placement is retained versus migrated behind the new compiler;
- exact town/wilderness recipe roster;
- whether slopes are geometry in the first C1H proof or stairs/riser transitions suffice;
- visual and mechanical acceptance thresholds;
- first realm/material pilot;
- offline unwrap package/tool choice when a real complex asset triggers it; and
- P10.10 budgets and device/accessibility projections.

No code, asset generation, package installation, worktree, CI expansion, merge, or push is authorized by this
study.
